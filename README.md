# 多维表格子系统

面向私募股权投资场景的指标协同多维表格子系统，在行业通用多维表格能力之上，自主研发与 J 博士业务平台相适配的指标字段映射、引用表自动创建、递归下钻、编辑回写与租户空间协同机制，使指标库与多维表格形成稳定的数据交互链路。

---

## 一、项目研发目标与内容

随着公司业务规模扩大，指标库中的数据具有字段类型多、引用关系复杂、需要逐层下钻和多人协同编辑等特点。传统固定表格和报表只能展示既定数据，难以同时满足指标结构动态变化、关联数据展开、编辑回写和租户隔离要求；同时，客户在业务发展过程中，指标口径、统计维度和协同方式会不断调整，传统按固定报表开发的方式在交付周期和维护成本上形成明显制约，难以快速响应客户需求。

本项目立项的目的，是在行业通用多维表格技术基础上，自主研发与 J 博士业务平台相适配的指标协同子系统，建立指标字段映射、引用表自动创建、递归下钻、编辑回写和租户空间协同机制，使指标库与多维表格形成稳定的数据交互链路，支撑客户在业务发展中快速调整指标展示和协同方式的需求。

---

## 二、创新点及突破点

市面上的多维表格产品（如飞书多维表格、Airtable 等）已具备字段、视图、公式、查找、汇总和协作等通用能力，但均面向通用办公场景设计，无法直接满足私募股权投资机构「投资指标数据跨系统协同维护、穿透式分析、受控合规」的业务需求。本项目针对这些需求自主研发，创新点及突破点如下：

- **指标数据与业务系统的双向实时联动**  
  突破市面多维表格作为独立数据源、只能人工录入或单向导入的局限，建立 J 博士指标库与多维表格的双向实时数据链路——表格中维护的指标数据可直接回写业务系统生效，实现「表格编辑、系统生效」的数据闭环，使指标数据与主系统保持实时一致。

- **投资穿透式递归下钻分析**  
  针对私募股权投资多层股权结构、投资穿透至底层标的的业务需求，实现按指标引用关系自动创建引用表并递归下钻，逐层展开投资结构与指标关系，支持从基金、项目到底层标的的多级穿透分析，突破了通用多维表格仅支持平面数据展示、无法表达投资层级关系的局限。

- **指标主数据驱动的表格模型自动构建**  
  以指标定义为主数据源，自动将指标字段、字典、用户和引用关系转换为多维表格字段模型并自动建表，指标口径、字段类型调整后表格结构自动跟随更新，实现「配置即表格」，避免了通用表格人工建表、口径变更后表格结构与数据不同步的问题。

- **金融受控协同编辑**  
  通用多维表格开放协作、人人可编辑，不满足金融数据合规要求。本系统在多人协同编辑指标的同时，通过主系统权限校验、业务脚本执行和回写控制实现受控编辑闭环，支持权限分级与操作审计，兼顾「多人协同维护」与「金融数据安全合规」。

- **AI 辅助指标协同**  
  将大模型能力融入指标协同流程，用户上传文件后 AI 自动识别并填写指标，替代手工录入，降低录入成本、提升指标维护效率，为投资指标协同提供智能化辅助。

- **信创数据库读写回写与国产化部署**  
  实现指标数据从国产信创数据库读取、在表格中协同编辑后回写至信创数据库，数据全程存储于信创环境，平台整体支持国产化环境部署运行，满足投资机构信息系统自主可控、国产化替代的部署要求。

## 三、研发的技术难点与结果不确定性

本项目并非在成熟多维表格产品上做简单接入，而是围绕指标协同场景自主研发业务适配层，涉及指标动态查询与表格结构的映射、引用递归下钻、受控回写等多个环节，各环节相互耦合，研发过程中存在真实的技术难点和失败风险：

- **动态 SQL 指标与表格静态结构的映射**  
  J 博士指标库中的指标并非静态字段，而是由动态查询 SQL（指标查询 SQL、详情 SQL、下钻数据 SQL）在运行时计算生成，字段集合随 SQL 变化而变化。将动态 SQL 的查询结果结构稳定映射为多维表格的静态字段模型，并在指标 SQL 调整后同步表格结构，是首要难点——映射一旦滞后，表格中会出现字段缺失、类型错配或历史数据与结构不一致，且问题往往在运行一段时间后才暴露。

- **引用表与递归下钻的自动创建**  
  根据指标引用关系自动创建引用表和递归下钻表时，需处理重复创建、循环关系、层级扩展和元数据变化。单层引用不能满足多级指标关系，重复创建又会形成冗余表和错误关联；递归下钻表的每一层由不同的动态数据 SQL 驱动，层级字段、参数透传和层级过深时的性能问题，都需要谨慎设计复用和边界控制。

- **指标口径变化时已建表格的迁移**  
  指标结构、口径、字典调整后，已创建的表格结构、关联字段和记录需同步更新，同时不能破坏用户已在表格中维护的数据。结构变更与存量数据迁移的顺序、兼容性和回滚，是研发中易出错的环节。

- **编辑回写与受控协同的一致性**  
  表格中维护的指标数据需回写业务系统生效，回写时机、失败补偿、与主系统数据的并发冲突处理，直接影响指标数据的准确性和一致性；同时，编辑需在业务脚本和受控规则约束下进行，避免绕过主系统业务逻辑。表格侧编辑与主系统侧数据如何保持实时一致，是跨系统数据协同中的关键难点。

- **信创环境下的数据读写与 AI 识别**  
  指标数据需在国产信创数据库中读取、编辑并回写，涉及建表、分页及相关 SQL 和 Java 逻辑的兼容差异，初期在国产环境下运行存在兼容问题；同时，用户上传文件后 AI 识别填写指标，识别准确率受文件版式、扫描质量和字段命名规范影响，复杂表格和不规范文件可能出现字段漏识别或错填，难以保证一次识别即正确，需要人工复核与持续优化。

上述难点表明，本项目的研发结果存在不确定性：各项关键技术均需通过多轮试验、失败、调整和迭代才能逐步收敛，研发周期和技术成果受多种因素影响，存在不能完全达到预期指标的风险。

## 四、已达到的技术指标

项目最终形成了 J 博士指标库与多维表格之间的自主业务适配层，完成字段语义转换、引用表创建、递归下钻、记录交互和编辑回写，通用表格能力与公司新增的指标协同能力通过独立模块和接口进行衔接，并已支撑私募股权投资管理系统各业务模块的稳定运行。围绕上述创新点，各项技术指标均已达成：

| 对应创新点 | 目标值或目标范围 | 最终实现结果 |
| --- | --- | --- |
| 指标数据与业务系统的双向实时联动 | 指标数据可跨系统协同维护、编辑回写生效 | 已形成指标库与表格的双向数据交互链路，支持编辑回写生效 |
| 投资穿透式递归下钻分析 | 支持从基金、项目到底层标的的多层级穿透分析 | 已实现引用表自动创建与递归下钻，支撑投资穿透式业务分析 |
| 指标主数据驱动的表格模型自动构建 | 指标口径调整后表格结构自动跟随、配置即用 | 已将 6 类主端字段编码映射为文本、数字、日期、单选和用户 5 类目标字段 |
| 金融受控协同编辑 | 支持权限分级、操作审计的受控协作 | 已形成只读 / 可编辑 2 种受控模式及相应权限校验、审计处理 |
| AI 辅助指标协同 | 支持用户上传文件后 AI 自动识别并填写指标 | 已实现 AI 识别填表能力并融入指标协同流程 |
| 信创数据库读写回写与国产化部署 | 指标数据支持从信创数据库读取并回写，平台国产化部署 | 已实现指标数据在国产信创数据库中的读取、编辑与回写 |

此外，项目还实现了：

- 针对引用表重复创建、循环关系、并发初始化和编辑回写等实际研发问题完成了多轮调整与验证。
- 形成了指标只读、可编辑、下钻记录编辑和主系统回写的一致性机制，以及租户空间和协作者协同机制。
- 平台底层能力已从单一指标展示扩展为可复用的指标协同运行机制，支撑投资业务多场景复用。

## 五、本地开发与启动

按下面步骤操作即可完成配置并启动项目。**只需启动一次（后台），前后台会一起跑。**

### 1. 运行方式说明

- **只启动一个服务**：在 `apps/nestjs-backend` 里执行 `pnpm dev`。
- **后台（NestJS）**：提供 API、数据库、WebSocket 等。
- **前台（Next.js）**：由后台在启动时通过 `NextService` 自动创建并挂载，**不需要单独起前台**。
- 访问 **http://localhost:3000** 即可使用完整应用（页面 + 接口）。

### 2. 环境要求

| 项目 | 要求 |
| --- | --- |
| Node.js | 使用 **v20.20.0**（见下方说明） |
| pnpm | ≥ 9.13.0 |
| PostgreSQL | 已安装并可连接 |
| Redis | 已安装并可连接 |

**Node 版本说明**：本项目用 **Node v20.20.0**，通过 `nvm use v20.20.0` 切换，**只影响当前终端，不会改你的 nvm 默认版本**。

### 3. 环境变量

- 主配置：`apps/nextjs-app/.env.development.local`（优先）
- 备选：`apps/nextjs-app/.env.development`
- 后端和 Prisma 都会从上述文件读取配置（尤其是 `PRISMA_DATABASE_URL`）。

| 变量 | 说明 | 示例 |
| --- | --- | --- |
| `PRISMA_DATABASE_URL` | 数据库连接串 | `postgresql://postgres:123456@localhost:5432/lltable?schema=public&statement_cache_size=1` |
| `PUBLIC_DATABASE_PROXY` | 数据库代理地址 | `localhost:5432` |
| `PORT` | 服务端口 | `3000` |
| `SOCKET_PORT` | WebSocket 端口 | `3001` |
| `PUBLIC_ORIGIN` | 前端访问地址 | `http://localhost:3000` |
| `NEXTJS_DIR` | Next 应用目录（相对后端） | `../nextjs-app` |

### 4. 首次启动

```bash
# 1. 进入项目根目录
cd <项目根目录>

# 2. 切换 Node 版本（仅当前终端）
nvm use v20.20.0

# 3. 安装依赖
pnpm install

# 4. 确认/编辑环境变量
# 确保存在 apps/nextjs-app/.env.development.local
# 按实际 Postgres 地址/密码修改 PRISMA_DATABASE_URL 与 PUBLIC_DATABASE_PROXY

# 5. 创建数据库（若尚未创建）
# 在 PostgreSQL 中执行：CREATE DATABASE lltable;

# 6. 执行迁移（生成 Prisma Client + 建表）
bash scripts/setup-and-migrate.sh

# 7. 启动项目（前后台一起）
cd apps/nestjs-backend
pnpm dev
```

浏览器访问：**http://localhost:3000**

### 5. 日常启动

```bash
cd <项目根目录>
nvm use v20.20.0
cd apps/nestjs-backend
pnpm dev
```

Debug 启动：

```bash
nvm use v20.20.0
cd apps/nestjs-backend
pnpm start-debug
# 执行后点击 F5 挂到工具监听服务
```

### 6. 常见问题

| 现象 | 处理 |
| --- | --- |
| `The table public.space does not exist` | 未做迁移，执行：`bash scripts/setup-and-migrate.sh` |
| 数据库连接失败 | 检查 Postgres 是否启动、`PRISMA_DATABASE_URL` / `PUBLIC_DATABASE_PROXY` 的 host/端口/密码 |
| 端口 3000 被占用 | `lsof -i:3000` 查进程并结束，或改 `.env.development.local` 里的 `PORT` |
| 不想用 nvm 改默认版本 | 只在需要跑本项目的终端里执行 `nvm use v20.20.0` 即可 |

### 7. AI 功能配置（可选）

AI 能力由实例级配置控制，需管理员账号在管理后台配置：

1. 管理员登录后访问：**http://localhost:3000/admin/setting**
2. 在「LLM API」中配置自定义模型或 AI Gateway
3. 添加服务商（如通义 Qwen）、填写 Base URL / API Key / 模型列表
4. 设置默认模型，打开「启用 AI」并保存

配置后即可使用 AI 识别填表、AI 字段生成等能力，无需在代码或 `.env` 中写死 API Key。
